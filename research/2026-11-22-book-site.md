# The book site: where it lives and what builds it

Researched 2026-11-22. The question: should the rendered book at `rubric.mattkelly.io` be GitHub Pages, or a site we host ourselves, and which tool turns the chapters into it?

## GitHub Pages

What it gives us, from GitHub's docs:

- **Limits.** A site of up to 1 GB, a soft limit of 100 GB of traffic a month, and deploys that time out after 10 minutes. The soft limit of 10 builds an hour does not apply to sites built by a custom Actions workflow ([limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).
- **Any build tool.** A custom workflow builds the site, packages it with `upload-pages-artifact` and publishes it with `deploy-pages`, so the generator is our choice, not Jekyll's ([custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)).
- **A custom domain.** A CNAME record from `rubric.mattkelly.io` to `mathisto.github.io` ([custom domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site)). With Cloudflare in front, the record must be DNS-only while GitHub issues the certificate; a proxied record blocks it ([Cloudflare community](https://community.cloudflare.com/t/github-pages-require-disabling-cfs-http-proxy/147401), [GitHub on HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)). Pages already sits behind Fastly, so DNS-only loses nothing important.

What it cannot do:

- **Response headers.** Pages sets its own headers and no others ([community discussion #13309](https://github.com/orgs/community/discussions/13309)). The one that matters to us: WebAssembly that uses threads needs cross-origin isolation (the COOP and COEP headers). The workaround, [coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker), forces a reload on first visit and has known reload-loop bugs. A single-threaded interpreter needs none of this.
- **Server logic.** No redirects beyond the basics, no server-side code, no logs.

## Hosting it ourselves

Campo on `web`, behind the Cloudflare tunnel, or a server on marge would allow anything: any headers, server code, logs, a live fork playground. The costs:

- **Uptime ties to the lab.** A public showpiece would go down whenever lovelace reboots or the tunnel drops. Marge avoids that, but it is a small VPS we patch ourselves.
- **Upkeep.** Certificates, deploy hooks and a build runner become ours to run.
- **No gain today.** The book is static Markdown. Nothing in it needs a server yet.

## Which tool builds the book

| Tool | Fit | Verdict |
| --- | --- | --- |
| [mdBook](https://rust-lang.github.io/mdBook/) 0.5.4 (2026-07-06) | One binary, maintained by the Rust project, builds the Rust book. Search, print view and themes built in. Chapter order comes from `SUMMARY.md`, and `README.md` becomes the front page ([index preprocessor](https://rust-lang.github.io/mdBook/format/configuration/preprocessors.html)). Highlighting is highlight.js, extensible with a bundle that knows Rubric ([syntax highlighting](https://rust-lang.github.io/mdBook/format/theme/syntax-highlighting.html)). Its one advisory, a search-page XSS, was fixed in 0.4.5 in 2021. | Adopt for now |
| Jekyll, the Pages default | No setup, but it makes pages, not a book: no chapter navigation and no search without plugins. | Reject |
| Material for MkDocs | In maintenance mode since November 2025; its team moved to Zensical ([announcement](https://squidfunk.github.io/mkdocs-material/blog/2025/11/05/zensical/)). | Reject |
| Zensical | The successor, about a year old. | Watch |
| Jupyter Book, Quarto | Built for notebooks and scientific publishing, and heavy for a plain Markdown book. | Reject |
| Docusaurus, VitePress | JavaScript site frameworks; more machinery than a book needs. | Reject |

### The long view: our own weaver

In Knuth's literate programming, the tool that typesets the book is part of the system, and the tangler has a twin called the weaver. A future chapter can write Rubric's own weaver, which would know the four kinds of code block, the rule anchors and the forks, and replace mdBook. Until then, mdBook is scaffolding, the same way Zig is.

## Decision

Matt adopted this on 2026-11-22. It replaces the earlier plan to serve the book from Campo.

1. Publish to GitHub Pages from a workflow that runs on every push to `main`: check the prose, build with a pinned, hash-checked mdBook, and deploy.
2. Point `rubric.mattkelly.io` at it with a DNS-only CNAME in Cloudflare.
3. Keep the site a plain folder of static files, so moving it is cheap. If the fork explorer ever needs threads or server code, the same folder moves to marge, and only the DNS record changes.
4. Replace mdBook with Rubric's own weaver once the book can write one.

Open detail for the first tools chapter: where the chapters sit. mdBook reads one source folder, and `README.md` at the repo root is the Incipit. Either the chapters live in a `book/` folder with a short root README pointing in, or the build copies the root README in before running mdBook. The second keeps GitHub's front page as the real Incipit.
