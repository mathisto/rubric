# Prior art

Surveyed 2026-11-22, before the repo exists. Four questions: who has written a language as a book, how executable specs keep prose and code together, how spec-first work with an LLM goes wrong, and how languages record their decisions and compare alternatives. Claims marked as checked were read on the primary page; the rest come from the survey and carry its links.

## Languages written as books

- **Knuth's WEB and CWEB.** TeX itself is a literate program. A tangler pulls the code out in whatever order the compiler needs, and a weaver typesets the book ([Knuth, 1984](https://www.cs.tufts.edu/~nr/cs257/archive/don-knuth/web.pdf)). The recurring complaint: the generated code is unreadable, and people edit it directly, so it drifts from the source.
- **Crafting Interpreters.** Checked in the repo. The code is the master copy, not the book. Java and C files carry markers such as `//> Scanning scanner-class` and `//< keyword-map`, and chapters pull snippets in with `^code name`. A split tool rebuilds the program as it stands at any chapter, and the tests run against each chapter's version ([source_file_parser.dart](https://github.com/munificent/craftinginterpreters/blob/master/tool/lib/src/source_file_parser.dart), [split_chapter.dart](https://github.com/munificent/craftinginterpreters/blob/master/tool/lib/src/split_chapter.dart)). A TODO admits that duplicate snippet names are not rejected.
- **Staged compilers.** Ghuloum's incremental approach yields a working compiler at every step ([Scheme Workshop 2006](https://www.schemeworkshop.org/2006/11-ghuloum.pdf)). Sandler's book keeps valid and invalid test programs for each chapter ([writing-a-c-compiler-tests](https://github.com/nlsandler/writing-a-c-compiler-tests)).
- **Axiom** tried to become literate late, and the rewrite is still unfinished years on ([axiom-developer, 2022](https://lists.nongnu.org:443/archive/html/axiom-developer/2022-07/msg00001.html)). Literate from commit 0 avoids that cost.
- **Modern tools.**
  - Lean's [Verso](https://verso.lean-lang.org/) type-checks every example while it builds the document.
  - [`mdbook test`](https://rust-lang.github.io/mdBook/cli/test.html) runs untagged blocks as Rust, a known trap.
  - [Entangled](https://entangled.github.io/manual.html) joins blocks of the same name in document order and can copy edits back into the Markdown.
  - Racket's [Scribble](https://docs.racket-lang.org/scribble/eval.html) hides setup code from readers.

## Executable specs

- **WebAssembly's SpecTec** generates the prose spec, the formal rules and an interpreter from one source. Writing the interpreter exposed bugs in the hand-written prose. Checked: the Wasm community group voted in March 2025 to write future editions in it ([announcement](https://webassembly.org/news/2025-03-27-spectec/), [PLDI 2024 paper](https://arxiv.org/abs/2311.07223)).
- **The Rust Reference.** Checked: compiler tests carry a `//@ reference: x.y.z` header that names the rule they cover, and a summary page shows which rules have tests ([test annotations](https://rust-lang.github.io/reference/dev-guide/rules/test-annotations.html)).
- **ECMAScript** has test262 as its conformance suite, and ESMeta extracts an interpreter from the spec's prose ([test262](https://github.com/tc39/test262), [ESMeta](https://github.com/es-meta/esmeta)).
- **Python's** reference is prose, and CPython's test suite settles what the prose leaves open ([introduction](https://docs.python.org/3/reference/introduction.html)). That split is the drift this book exists to prevent.
- **The Go spec** marks the places where implementations may differ, rather than leaving them vague ([Go spec](https://go.dev/ref/spec)).
- **Tools for later:**
  - Racket's [`#lang`](https://docs.racket-lang.org/guide/hash-lang_reader.html) swaps the reader for each file.
  - [Ohm](https://ohmjs.org/editor) keeps the grammar apart from its semantics and has a live editor.
  - [PLT Redex](https://docs.racket-lang.org/redex) tests semantic rules with random programs.
  - [Tree-sitter](https://tree-sitter.github.io/tree-sitter/) gives editors incremental parsing.

## Spec-first work with an LLM

- **Fowler's three levels.** Checked: spec-first, spec-anchored (the spec stays after the work, for maintenance) and spec-as-source. He also saw different code come out of the same spec on different runs ([Fowler on SDD tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
- **Spec Kit and Kiro** produce many files per feature, which are tedious to review, and Kiro's phases are heavy for small changes. Kiro's acceptance criteria are written to be testable, which is worth keeping ([Spec Kit](https://github.blog/2025-09-02-spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)).
- **Reported failures:** specs go stale within days because agents fix things in code only, and reviewing a spec costs as much as reviewing code. The proposed fix is a build that fails when a spec's test is missing or failing ([InfoQ](https://infoq.com/articles/when-spec-driven-development-pays-off)).
- **Cucumber's** living documentation decays when scenarios describe the screen, not the behavior, and when failing scenarios are written off as stale ([anti-patterns](https://cucumber.io/blog/cucumber-anti-patterns-part-two/)). **Concordion** runs the prose document itself, instrumented with hidden attributes ([Concordion](https://concordion.org/instrumenting/java/html)).
- **Doctests.**
  - Python's [doctest](https://docs.python.org/3/library/doctest.html) breaks on exact output and leaks state between examples.
  - Elixir's [`doctest_file`](https://ex-unit.hexdocs.pm/ExUnit.DocTest.html) runs examples straight from a Markdown file.
  - Go is checked: an example without an output comment is compiled but never run ([Go blog](https://go.dev/blog/examples)). It passes without proving anything.
- **No public project** was found that writes the prose first and lets an LLM write the code, commit by commit. We make no claim to be first; the history will speak for itself.

## Decision records and alternatives

- **Python** keeps rejected PEPs in its index ([PEP 1](https://peps.python.org/1)). Rust's accepted RFCs are frozen, and later changes become new RFCs ([Rust RFCs](https://rust-lang.github.io/rfcs/)). Swift keeps a list of commonly rejected changes. Architecture decision records follow the same pattern: a status, and a superseding record rather than an edit ([ADR](https://www.martinfowler.com/bliki/ArchitectureDecisionRecord.html)).
- **Roc** wrote up its reversals as decisions of their own ([Roc](https://www.roc-lang.org/)). Hare and Gleam publish non-goals ([Hare](https://harelang.org/blog/2023-11-08-100-year-language/), [Gleam 1.0](https://gleam.run/news/gleam-version-1/)).
- **Evidence.** Quorum tests syntax choices in controlled studies. Hedy teaches through graded levels ([Hedy research](https://hedy.org/research/)). Pyret's researchers measured how well error messages point at the real problem ([Wrenn and Krishnamurthi, 2017](https://par.nsf.gov/servlets/purl/10067512)).
- **Comparing variants.**
  - [7GUIs](https://eugenkiss.github.io/7guis/) gives every toolkit the same seven tasks; its author later found some tasks artificial.
  - [PL Zoo](https://plzoo.andrej.com/) keeps one small, complete interpreter per design.
  - [Compiler Explorer](https://godbolt.org/) shows compilers side by side.

## What we adopt

Matt adopted all seven on 2026-11-22.

1. **The book is the master; the generated code is committed and checked.**
   - The tangler writes Zig into `gen/`, and each file names the chapter and line it came from.
   - The build regenerates `gen/` and fails if it differs from what is committed, so hand edits cannot survive.
   - GitHub and editors still show real source.

   This is Knuth's direction with a guard against his tool's known drift. Crafting Interpreters' code-first direction fits a finished book but not our prose-first rule.
2. **Generated code is reviewed once and committed.** The LLM writes it when its chapter lands, and nobody regenerates it on every build, since two runs from one spec give different code. The book is spec-anchored, in Fowler's terms.
3. **The gate checks parity.**
   - Every fence has a tag.
   - Every `rubric example` and `rubric error` runs; none passes without running.
   - Every rule section has at least one example, as Rust's Reference does with rule IDs.
   - A duplicate block name is an error.
4. **Every chapter builds.** The program as it stands at chapter N compiles and passes chapter N's examples, as Crafting Interpreters and Ghuloum do.
5. **Hidden setup.** A `rubric setup` fence holds code an example needs but readers don't, as Scribble does.
6. **Decision sections** carry a status (accepted, rejected or superseded) and are frozen once accepted. A change is a new decision that points back. The book keeps an index of rejected ideas and a list of non-goals.
7. **Forks** all express a fixed reference corpus of small, realistic programs, and every verdict cites what the corpus showed.

## Later, or not at all

- Racket-style reader swapping and an Ohm-based grammar view are candidates for the fork explorer, not for now.
- Random testing of rules, in the style of PLT Redex, once the semantics chapters exist.
- Tree-sitter, once the grammar settles.
- A single-source spec language in the style of SpecTec, or K, is more machinery than the book needs.
- Spec-as-source (Tessl) is rejected, because regenerating the code on every build is not repeatable.
